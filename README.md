# 🎭 舞台换景排练系统

供舞台监督排练换景使用的网页应用：管理道具与区位、按提示号录入一组组同时发生的道具转移，并在任意增删改后**按提示号全量重放**，实时展示每组提示的校验结果与最终区位分布；在此基础上维护**换景人员及其搬运资格**，自动为每条生效提示生成**逐提示岗位表**，并对整场生效提示**联合求解连场轮换排班**（相邻生效提示同一人员不得连场，解不出时报告首个无法形成可行前缀的提示号及其前一条生效提示号）；还可临时添加多条「人员 × 提示号闭区间」缺席规则，**只在内存中试排**，不保存规则、不改动正式排班。另有独立的**换景通道规划**模块：在区位间维护**无向通道**（禁止自环与重复连接，删除区位自动清理关联通道），对每条重放生效的提示**逐组联合搜索互不共边的简单路径组合**（不能逐条固定最短路），有解时列出每条转移的完整经过区位，无解时标出提示号与受影响转移并区分**端点不连通**与**通道争用**；线路随区位、通道与提示变更实时重算，作为独立预警展示。

技术栈：Node.js + Express + SQLite（better-sqlite3）+ 原生 JavaScript（无前端框架）。

## 业务规则

- **区位容量**：「后台」可容纳任意数量道具；其余每个区位最多容纳一件。
- **提示（Cue）**：提示号唯一，重放按提示号升序进行；每组提示包含若干条同时发生的转移。
- **同组限制**：同组内每件道具最多转移一次（数据库唯一约束 + 录入校验双重保证）。
- **整组校验、整组提交**：
  - 每条转移基于**该组变动前**的状态校验来源区位（道具必须确实在来源区位）；
  - 整组应用后，除后台外任何区位不得被多件道具占用；
  - 任一条件不满足则**整组不生效**（状态回滚到变动前），并展示全部冲突原因；
  - 因为占用校验针对的是整组完成后的状态，所以**同组互换区位是允许的**（如 A、B 两件道具互换位置）。
- **全量重放**：插入、修改或删除任意提示后，从道具初始区位出发按提示号重放全部提示，页面展示每组结果（生效 / 未生效及原因）与最终区位。
- **失败提示的冲突溯源**：重放结果为每组提示附带结构化溯源 `trace`（成功组恒为空），在失败提示旁与原有错误文案一并展示：
  - **来源区位不符**：列出道具当前区位及其**最后一次成功转移的提示号**；从未成功转移的道具标记为「初始区位」；
  - **容量冲突**：列出试算后同占该区位的全部道具，标明各道具**是否由本组转入**，及其此前最后一次成功转移的提示号；
  - 溯源随提示号顺序更新：同组转移依据组前状态，**失败组既不改变位置也不改变溯源**，只有整组生效后才把组内道具的「最后成功转移」更新为该组提示号。
- **批量平移提示号**：输入闭区间起止号与非零整数位移，先预览列出区间内每条提示的「原号 → 新号」。执行时校验：区间内至少一条提示、每个新号都是安全正整数、且不与区间外的提示号冲突；任一不满足则**整批拒绝**并标出冲突号。校验通过后在**单个数据库事务**中同时改写提示主键与转移的提示号引用（备注、转移内容与组内顺序保持不变），成功后按新号全量重放并刷新页面；提示的编辑、删除与试排预览均识别改后的号码。
- **试排预览（不写库）**：在提示录入/编辑表单可先「试排预览」。服务端沿用保存时的字段校验，把草稿按提示号插入或替换到内存中的序列，分别重放现行序列与假设序列，列出**生效状态发生变化的提示及前后冲突原因**，以及**最终区位发生变化的道具**；草稿不合法时直接返回具体错误。整个过程只在内存中重放，不写数据库；保存仍使用原有新增/替换接口。
- **现场偏差推演（不写库）**：舞台监督选择一条**已执行完的提示号作为断点**，录入**部分道具**的现场区位，未录入者沿用该断点重放后的计划区位。系统先按现有规则把提示**重放至断点**，校验现场区位（区位必须存在、普通区位不得重叠，后台不限）；校验通过后再以校正后的现场状态**接续重放断点之后的全部提示**，失败组仍按同一规则**整组不生效**。页面并列展示：断点处计划/现场区位差异、后续每条提示在原计划与现场推演中的生效状态与冲突原因（含冲突溯源）、推演结束后的最终道具区位差异。现场录入道具的溯源标记为「现场校正」。推演全程只在内存中进行，**不修改提示、道具初始区位或数据库**，复用同一套重放规则。
- **换景人员分配（逐提示岗位表）**：维护工作人员及其**可搬运的道具名单**（搬运资格），系统以**最新全量重放结果**为准自动排岗：
  - 仅对**整组生效**的提示分配人员；**失败提示标记为「无需执行」**，不排岗；
  - 组内**每条道具转移占一个同时执行的岗位**；
  - **同一人员在同一组内最多承担一个岗位**（不同组先后执行，可重复出现）；
  - 人员必须**具备该道具的搬运资格**才能承担对应岗位；
  - 服务端对整组求**完整匹配**（二分图最大匹配，增广路算法），**不按转移录入顺序贪心分配**——贪心会让先录入的转移占掉唯一合适的人（例如同组「屏风（张三/王五可搬）、桌子（仅张三可搬）」，必须把先录的屏风改派王五，桌子才能分给张三）；
  - 无法整组覆盖时，该组标记为**「人手不足」**并**标出未覆盖道具**，**不输出部分岗位表**，同时给出**「资格瓶颈诊断」**：基于整组最大匹配，从全部未匹配转移出发沿资格竞争关系（道具 → 合格人员 → 该人员匹配承担的转移 → 道具……）做交替路可达分析，再把可达子图切成**互不相连的竞争簇**——每簇给出**缺口人数**、参与竞争的**道具名单**（簇内已匹配道具同样是瓶颈的一部分，**不能只把当前未匹配道具当作瓶颈**）与**合格人员名单**；簇外人员/资格与该缺口无关，为簇内道具新增可搬人员或补授资格即可缓解；
  - 可完整排岗（`ok`）与重放未生效、无需执行（`skipped`）的组**不附诊断**；
  - 人员、资格或提示的任何变化都会触发岗位表按最新数据**整体重算**（岗位表不落地存储，每次由最新数据实时计算）；
  - 道具被删除时，各人员对该道具的搬运资格一并清理。
- **连场轮换排班（整场联合求解）**：在逐提示岗位表旁为舞台监督提供**整场人员安排**。与逐提示独立排岗不同，本排班把全场提示串起来联合求解：
  - **仅纳入全量重放生效的提示**；失败提示**不计轮次**——不参与排班，也不隔开前后两条生效提示（相邻判定只看生效提示序列，中间夹多少失败提示都不影响）；
  - 每条转移仍须由**具备该道具搬运资格的不同人员**承担，同一人员在同一条提示内最多一岗（沿用整组完整匹配约束）；
  - 额外的连场约束：**同一人员不得出现在相邻两条生效提示中**；
  - 排班对**整场联合求解**：逐组各自可行不等于连起来可行（相邻两组的合格人员可能恰为同一人），求解器对每组枚举全部可行动用人员集合，再沿生效序列做动态规划并回溯，**允许调整前序提示的合法分配**为后续提示腾出人员；
  - 若无法全覆盖，只显示**首个无法形成可行前缀的提示号及其前一条生效提示号**（首条即无解时前一条标记为「无」），并区分原因：`understaffed`（该提示单独就无法整组覆盖，可参照逐提示岗位表的资格瓶颈诊断）与 `rotation`（单独可排，但与任何可行前缀都必然让同一人连场）；**不输出部分岗位表**；
  - 全场可排时输出**逐轮岗位表**与**整场人员安排矩阵**（行＝人员、列＝连场轮次，悬停查看转移明细）；
  - 人员、资格或提示变更后随全量状态**实时重算**（不落地存储），提供页面入口（⑧ 卡片右上链接与页面底部 ⑨ 卡片）与查询 API（`GET /api/rotation`，并随 `GET /api/state` 一并返回）。
- **临时缺席试排（不写库）**：舞台监督在页面临时添加**多条规则**，每条指定一名**现有人员**与一个**提示号闭区间** `[from, to]`，点击「开始临时缺席试排」后**只在内存中计算**——不保存规则、不改动正式排班或数据库：
  - 区间按提示号覆盖**全量重放后生效**的提示；**失败提示不占轮次**（落在失败提示号上的区间不影响任何轮次；区间内没有任何生效提示时该规则会原样回显但对结果无影响）；
  - 同一人员可被多条规则覆盖，**重叠规则取并集**（在任一条覆盖该提示号的规则区间内即缺席），完全相同的重复规则自动去重；
  - 某轮缺席的人员**不能出场**（从该轮可行动用人员中剔除），**区间外仍可参与**；
  - 其余约束完全沿用正式排班：**搬运资格、组内一人一岗、相邻生效提示不得同人**；对整场**联合求解并允许回溯调整前序分配**（与 `rotation.js` 同一套枚举＋动态规划求解核心，逐轮传入可出场人员掩码）；
  - 可行时展示**逐轮岗位与人员汇总**（每轮标注本轮缺席人员）与人员 × 轮次矩阵（缺席格标注「缺席」），并回显每条规则覆盖到的生效提示与轮次；
  - 无解时**只报告首个无法形成可行前缀的提示号、其前一条生效提示号与原因**（`understaffed`：缺席叠加资格后本组单独无法整组覆盖，附本轮缺席人员；`rotation`：单独可排但与任何可行前缀都必然同人连场），**不显示部分岗位**；
  - 服务端校验**未知人员与无效区间**（起止号必须为正整数、起点不得大于结束号），任一条不合法则整次拒绝并逐条列出原因；
  - 提供独立 API（`POST /api/rotation/absence/trial`）与独立页面入口（⑩ 卡片，可由 ⑨ 卡片右上角链接跳转）；人员、资格或提示一有变化，旧试排结果即清空。
- **换景通道（区位间无向边）**：在页面 ⑪ 卡片维护区位之间的**无向通道**，通道供道具换景时通行：
  - 通道**不区分方向**，提交 `(A, B)` 与 `(B, A)` 视为同一条，服务端把端点规范化为字典序后落库；
  - **禁止自环**（两个端点不能是同一区位）与**重复连接**（同一对区位只能有一条通道），由入参校验与数据库 `CHECK (loc_a < loc_b)` + 主键双重拒绝；
  - **删除区位时自动清理其关联的全部通道**（表上两端外键均为 `ON DELETE CASCADE`，服务端删除区位时也在同一事务中显式删除）；区位被道具或转移引用时仍按原规则禁止删除。
- **换景通道规划（逐组联合求解，独立预警）**：系统对每条**全量重放整组生效**的提示逐组规划换景线路（**失败提示整组不执行，不参与规划**，仅在汇总中注明条数）：
  - 同组内**每条道具转移**（来源区位 → 目标区位）须在通道图上选择一条**简单路径**（不重复经过同一区位）；
  - **任意两条路径不得共用同一条通道**（通道是无向的，两个方向都算占用；路径在中间区位相遇不算冲突）；
  - 必须**联合搜索可行组合，不能逐条固定最短路**：逐条取最短可能占掉后一条转移的唯一桥梁，而把前一条改走稍长的绕行路径后整组其实可解。求解器先对每条转移按长度升序枚举**全部简单路径**（最短优先），再以 MRV 顺序（候选路径最少的转移优先）做带回溯与前向约束传播的联合搜索，允许回头调整前序转移的选路；命中的第一个解优先采用较短路径，结果确定；
  - **有可行组合**时展示该组每条转移的**完整经过区位**（来源 → … → 目标）与经过通道段数；
  - **无解时标出提示号和受影响转移**，并区分两类原因：
    - **端点不连通**（`disconnected`）：某条转移的来源与目标区位在通道图上根本不在同一连通分量（BFS 不可达），与其他转移如何选路无关；受影响转移逐条列出；
    - **通道争用**（`contention`）：每条转移的端点各自可达，但不存在一组两两不共边的路径；附**争用簇**诊断——把转移按**极小不可行子集**（自身无法联合排开、删掉其中任意一条转移后即可排开的转移集合）分簇，逐簇列出卷入争用的转移，帮助判断该为哪几条通道补建平行通道；不属于任何极小簇、去掉也不影响可行性的转移不列为受影响；
  - 线路结果**不落地存储**，随区位、通道与提示的任何变更随全量状态**实时重算**，在页面 ⑫ 卡片以**独立预警**展示：顶部浓缩预警条逐行标出问题提示号、原因与受影响转移，下方再逐组列出完整线路或争用簇；提供独立查询 API（`GET /api/routing`，并随 `GET /api/state` 一并返回）；异常规模下设有路径 / 子集枚举上限保护，超限组标记 `limited` / 诊断截断提示而非超时。

## 快速开始（Docker，一条命令）

```bash
docker compose up --build
```

该命令会自动完成：构建镜像 → 安装依赖 → 首次启动时初始化 SQLite 数据库（建表 + 写入示例数据）→ 启动服务。

启动后访问（Web 页面与 API 使用同一端口 **3000**）：

- Web 页面：**http://localhost:3000**
- API：例如 **http://localhost:3000/api/state** 、 **http://localhost:3000/api/assignments** 、 **http://localhost:3000/api/rotation** 、 **http://localhost:3000/api/routing** 与 **http://localhost:3000/api/rotation/absence/trial**（POST，同为 3000 端口）

> 示例数据包含 8 个区位、5 件道具、3 名换景人员、4 条提示（10 / 20 / 30 / 40 号）与 8 条无向通道。其中 30 号提示故意与 20 号冲突，用于演示「整组不生效 + 冲突原因」；10 号提示演示「同组互换区位」，且同组中桌子仅张三能搬、屏风须改派王五，演示岗位分配不按录入顺序贪心；40 号提示的两件道具只有李四一人都能搬，演示「人手不足 + 未覆盖道具」及资格瓶颈诊断（单个竞争簇：花瓶、宝剑争夺李四，缺 1 人，未匹配道具另加标记）。
>
> 同一套示例数据也用于演示**连场轮换排班**：生效提示为 10 / 20 / 40（30 失败不计轮次），40 号因花瓶、宝剑仅李四一人可搬而成为首个无法形成可行前缀的提示，页面 ⑨ 报告会停在「提示 40，前一条生效提示 20」且不输出部分岗位表；新增一名可搬花瓶与宝剑的人员后会变成**连场轮换冲突**（40 仍与 20 抢人），再为另一名人员补授宝剑资格（让 20 号可换别人承担）即可全场排开，可据此观察联合求解对前序提示分配的调整。
>
> 全场可排后可在 **⑩ 临时缺席试排**继续观察缺席规则：如令 20 号唯一在场人选临时缺席（区间 `[20,20]`），联合求解会**回溯调整前序分配**仍排开全场；令某人在 40 号缺席则可能转为「人手不足」或「连场轮换冲突」，页面只报首个无法形成可行前缀的提示号与原因。试排只在内存中进行，刷新页面或改动任何数据后规则即消失。
>
> 通道拓扑同时用于演示 **⑫ 换景通道规划预警**：后台与舞台中央之间有一短（后台—上场门—舞台中央，2 段）一长（后台—高台—侧台—舞台中央，3 段）两条互不共边的路径，10 号提示的桌子、屏风互换若**逐条取最短**会抢「后台—上场门 / 上场门—舞台中央」通道，联合搜索把其中一件改走经高台、侧台的长路径即得到可行组合（可对照逐组线路查看完整经过区位）；40 号提示的花瓶、宝剑撤向后台时**各自端点连通**，但舞台左、舞台右只经「下场门」一侧连回后台，两条路径都必经「下场门—后台」这同一条通道，构成**通道争用**，预警按争用簇标出提示号 40 与两件受影响道具（与岗位表的「人手不足」是相互独立的两类预警）；在 ⑪ 中删除「侧台」（其无道具、无转移引用，可直接删除）会连坐清掉两条通道，10 号随即变为争用；再删掉「下场门—舞台左」之类通道则可观察**端点不连通**与争用的区别。

停止并删除容器（数据保留在命名卷 `stage-data` 中）：

```bash
docker compose down          # 如需同时清空数据：docker compose down -v
```

## 本地开发（不用 Docker）

要求 Node.js ≥ 18：

```bash
npm ci        # 安装依赖
npm start     # 初始化数据并启动，Web 与 API 均访问 http://localhost:3000（如 /api/state）
```

删除 `./data` 目录后重启即可重置为示例数据。

## 页面使用

1. **① 区位**：增删区位（「后台」为固有区位不可删；被道具或提示引用的区位不可删）。
2. **② 道具与初始区位**：新增道具并指定初始区位（非后台区位初始只能放一件）；可改初始区位、删除道具。
3. **③ 录入提示**：填提示号与备注，添加若干条「道具 / 来源 / 目标」转移后保存；点击列表中的「编辑」可修改整组。
   - **🧪 试排预览（入口：③ 录入提示表单内的「试排预览（不保存）」按钮）**：保存前先按提示号把草稿插入或替换到内存中的序列，不写库。面板会展示哪些提示的生效状态发生了变化（现行 → 假设，含冲突原因），以及最终区位发生变化的道具；草稿不合法时显示具体错误。表单内容一旦改动，旧预览自动清除，需要重新预览。
4. **④ 提示序列**：按提示号排列，每条提示标注 ✓ 已生效 / ✗ 整组未生效及冲突原因，失败提示下方附结构化「冲突溯源」（来源不符的道具当前区位与最后成功转移提示号；容量冲突的同占道具、是否本组转入及各自最后成功转移提示号），可编辑、删除。
   - **批量平移提示号（入口：④ 卡片顶部）**：填起始号、结束号（闭区间）与非零整数位移 → 点「预览平移」列出区间内每条提示的原号 → 新号；若新号与区间外提示冲突会逐条标红并禁用执行。确认无误后点「执行平移」，服务端在单个事务中完成整批改写并全量重放，页面随即刷新为新号。输入一旦改动需重新预览。
5. **⑤ 重放结果与最终区位**：逐组展示重放结论（失败提示同样附冲突溯源），看板展示全部提示重放后的最终道具分布。
6. **⑥ 现场偏差推演（入口：页面底部同名卡片，整页宽）**：选择已执行完的提示号作为断点 → 在每件道具的「现场区位」下拉中选择实际位置（留空＝沿用断点处计划区位）→ 点「🎯 开始现场推演」。面板并列展示：①断点处计划/现场区位差异；②断点之后每条提示在原计划与现场推演中的生效状态、冲突原因与结构化溯源（翻转的提示会高亮，失败组仍整组不生效）；③推演结束后的最终道具区位差异。现场区位重叠或不存在时整次推演被拒绝并标出冲突区位；推演仅在内存中进行，不写库。
7. **⑦ 换景人员与搬运资格**：添加/删除人员，并为每个人员授予或移除单件道具的搬运资格（资格以标签形式展示，点 ✕ 移除；下拉选择未具备的道具后点「＋ 授予资格」）。任何变化都会让右侧岗位表立即按最新数据重算。
8. **⑧ 逐提示岗位表**：按提示号逐组展示排岗结果——人员齐备的组列出完整岗位表（岗位序号 / 道具 / 转移 / 担当）；人手不足的组标红并列出未覆盖道具（不输出部分岗位表），其下展示**「资格瓶颈诊断」**：按互不相连的竞争簇逐簇列出**缺口人数、竞争道具名单（簇内已匹配道具也在其中，当前未匹配道具另加标记）与合格人员名单**；重放未生效的组标记「无需执行」且不显示诊断。顶部汇总各状态组数。
9. **⑨ 连场轮换排班（入口：⑧ 卡片右上角「连场轮换排班 →」，或直接滚动到页面底部同名整页宽卡片）**：把整场生效提示按提示号串成连场轮次（失败提示不计轮次、不隔开前后轮）联合求解——每条转移由具备资格的人员承担、同组每人一岗，且同一人员不得出现在相邻两条生效提示中。顶部用轮次条展示生效提示序列；可全场排开时列出**逐轮岗位表**（联合求解可能调整了前序提示的分配）与**整场人员安排矩阵**（行＝人员、列＝轮次，格内为本轮搬运道具，悬停看转移明细）；无法全覆盖时只显示**首个无法形成可行前缀的提示号及其前一条生效提示号**与原因（本组人手不足 / 与前序轮换冲突），**不输出部分岗位表**。人员、资格或提示一有变化即随整页实时重算。
10. **⑩ 临时缺席试排（入口：⑨ 卡片右上角「临时缺席试排 →」，或直接滚动到页面底部同名整页宽卡片；访问 http://localhost:3000 即可使用）**：点「＋ 添加一条规则」添加多行，每行选择一名**现有人员**并填写**提示号闭区间**起止号，点「🧯 开始临时缺席试排」。系统校验未知人员与无效区间（正整数、起 ≤ 止）后，按最新全量重放取生效提示轮次，把规则按提示号覆盖到轮次（失败提示不占轮次、重叠取并集），沿用搬运资格 / 一人一岗 / 相邻轮不同人约束对整场联合求解。可行时面板回显每条规则覆盖的生效提示与轮次、**逐轮岗位与人员汇总**（本轮缺席人员单独标注）及人员 × 轮次矩阵（缺席格标「缺席」，区间外照常出场）；无解时只显示首个无法形成可行前缀的提示号、前一条生效提示号与原因（本组人手不足 / 连场轮换冲突，附本轮缺席人员），不显示部分岗位。整个试排只在内存中进行：规则不保存、正式排班与数据库均不改动；清空规则可用「清空规则」按钮，人员 / 资格 / 提示变化后旧结果自动失效。
11. **⑪ 换景通道（入口：页面底部同名卡片；访问 http://localhost:3000 即可使用）**：在两个下拉中各选一个区位后「添加通道」，通道以 `A — B` 标签列出（无向，不区分方向）；点标签上的 ✕ 删除通道。两个端点相同（自环）或同一对区位重复连接会被拒绝（页面提示 + 数据库约束双重保证）；删除区位时其全部关联通道在同一事务中自动清理。
12. **⑫ 换景通道规划预警（入口：⑪ 卡片右上角「通道规划预警 →」，与 ⑪ 同处页面底部一行；访问 http://localhost:3000 即可使用）**：仅对**重放生效提示**逐组规划，结果随区位 / 通道 / 提示变更**实时重算**。顶部汇总各状态组数，有问题时以独立预警条逐行标出**提示号、原因（端点不连通 / 通道争用）与受影响转移**；下方逐组展示——可行组列出每条转移的**完整经过区位**与通道段数（同组路径两两不共边，联合搜索可能让某条转移绕行而非取最短路）；端点不连通组逐条列出无路可达的转移；通道争用组按**争用簇**（极小不可行子集）列出卷入争用的转移。失败（未生效）提示不参与规划，仅在汇总中注明条数。

> 访问入口与地址：`docker compose up --build` 后用浏览器打开 **http://localhost:3000**（Web 页面），API 同样走 **3000** 端口（如 http://localhost:3000/api/assignments、http://localhost:3000/api/rotation、http://localhost:3000/api/routing、POST http://localhost:3000/api/rotation/absence/trial）；试排预览按钮位于页面「③ 录入提示」表单中，现场偏差推演位于页面「⑥ 现场偏差推演」卡片，连场轮换排班位于页面底部「⑨ 连场轮换排班」卡片（也可从 ⑧ 卡片右上角链接跳转），临时缺席试排位于页面底部「⑩ 临时缺席试排」卡片（也可从 ⑨ 卡片右上角链接跳转），换景通道维护与通道规划预警位于页面底部「⑪ 换景通道」「⑫ 换景通道规划预警」卡片（两张卡片右上角可互相跳转）（默认宿主机端口 **3000**；改为 `"8080:3000"` 后 Web/API 均改访问 http://localhost:8080）。

## API 一览

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/state` | 全量状态：区位、道具、通道（`passages`，每项 `{a, b}` 为无向通道两端）、提示（含转移）、重放结果与最终区位、人员（含搬运资格）、逐提示岗位表、连场轮换排班与换景通道规划（`routing`，字段同 `/api/routing`）；重放结果每组含 `trace` 结构化冲突溯源（`sourceMismatches`：道具当前区位与最后成功转移提示号，`lastMovedCue` 为 `null` 表示初始区位；`capacityConflicts`：试算后同占道具、`movedIn` 是否本组转入及各自最后成功转移提示号）；岗位表中的人手不足组含 `diagnosis` 资格瓶颈诊断（字段同 `/api/assignments`）；`rotation` 字段为连场轮换排班（字段同 `/api/rotation`），人员或资格变化后随全量状态实时重算 |
| POST / DELETE | `/api/locations` `/api/locations/:name` | 新增 / 删除区位（删除区位时其关联通道在同一事务中一并清理） |
| POST / DELETE | `/api/passages` `/api/passages/:a/:b` | 新增 / 删除区位间无向通道：入参 `{a, b}`，端点自动规范化（`(A,B)` 与 `(B,A)` 等价）；两端相同返回 400（禁止自环），同一对区位重复连接返回 409（数据库 `CHECK (loc_a < loc_b)` + 主键双重保证）；删除不存在的通道返回 404 |
| POST / PUT / DELETE | `/api/props` `/api/props/:name` | 新增 / 改初始区位 / 删除道具（删除道具时其搬运资格一并清理） |
| POST / PUT / DELETE | `/api/cues` `/api/cues/:number` | 新增 / 整组替换 / 删除提示 |
| POST / DELETE | `/api/staff` `/api/staff/:name` | 新增 / 删除换景人员（删除人员时其搬运资格级联删除） |
| POST / DELETE | `/api/staff/:name/quals` `/api/staff/:name/quals/:prop` | 为人员授予 / 移除某件道具的搬运资格 |
| GET | `/api/assignments` | 逐提示岗位表（按最新重放结果与人员资格实时计算）：每组含 `status`（`ok` 人员齐备 / `understaffed` 人手不足 / `skipped` 无需执行）、`positions` 完整岗位表（仅 `ok` 时非空，每条转移一岗）、`uncovered` 未覆盖道具（仅 `understaffed` 时非空）与资格瓶颈诊断 `diagnosis`（仅 `understaffed` 时非空；`ok` / `skipped` 恒为 `null`）：`shortage` 缺口总数、`clusters[]` 每个互不相连竞争簇的 `shortage` 簇缺口人数、`props` 竞争道具名单（含簇内已匹配道具）、`uncoveredProps` 簇内当前未匹配道具、`staff` 合格人员名单；并附各状态组数汇总 `summary` |
| GET | `/api/rotation` | 连场轮换排班（整场联合求解，按最新数据实时计算）：`effectiveCueNumbers` 按重放顺序列出参与轮次的生效提示号（失败提示不在其中、不计轮次），`skippedCueCount` 失败提示数。`status` 为 `ok` 时：`rounds[]` 逐轮岗位表（`round` 连场轮次、`number` 提示号、`positions[]` 每条 `{prop, from, to, staff}`、`usedStaff` 本轮动用人员，相邻两轮不相交），`roster[]` 按人员汇总整场安排（`cues` 出场提示号、`positionCount` 岗位数、`appearances` 逐轮岗位明细），`summary` 含生效/失败提示数、参与人员数；`status` 为 `blocked` 时无 `rounds` / `roster`（不输出部分岗位表），由 `block` 给出 `number` 首个无法形成可行前缀的提示号、`previousEffectiveCue` 其前一条生效提示号（首条即无解为 `null`）、`reason`（`understaffed` 本组单独无法整组覆盖 / `rotation` 单独可行但与任意可行前缀都同人冲突）、`soloFeasible` 与 `compatibleWithPrevious` 诊断计数；`status` 为 `empty` 表示无生效提示；`limited` 为异常规模下的枚举上限保护 |
| GET | `/api/routing` | 换景通道规划（逐组边不相交简单路径联合求解，按最新区位 / 通道 / 提示实时计算，不落地）：`groups[]` 每项对应一条重放生效提示（失败提示不参与），`status` 为 `ok` 时 `routes[]` 给出每条转移的 `prop` / `from` / `to` / `path`（完整经过区位数组）/ `edges`（占用通道键）/ `hops`（通道段数），同组任意两条路径不共边；`status` 为 `disconnected` 时由 `disconnected[]` 逐条列出 `{index, prop, from, to}` 端点不连通的转移；`status` 为 `contention` 时各端点均连通但无不共边组合，`contention.clusters[]` 按极小不可行子集分簇（每簇 `transfers[]` 为卷入争用的转移），`contention.affected[]` 为全部受影响转移下标，`truncated` 表示诊断是否因子集枚举超限退化为全组；`status` 为 `limited` 时附 `limited`（单条转移简单路径数超上限，未计算）。顶层 `status` 为 `ok`（全部可行）/ `error`（至少一组无解）/ `empty`（无生效提示），`effectiveCueCount` / `skippedCueCount` 与 `summary` 给出各组状态计数与受影响转移总数 |
| POST | `/api/rotation/absence/trial` | 临时缺席试排（**只在内存计算，不保存规则、不改动正式排班或数据库**）：入参 `{rules: [{staff, from, to}]}`，每条指定现有人员与提示号闭区间。服务端先校验未知人员与无效区间（起止须为正整数、起 ≤ 止），不通过返回 400 并在 `errors[]` 逐条列出；通过后按最新全量重放取生效提示轮次（失败提示不占轮次），重叠规则取并集逐轮剔除缺席人员，沿用资格 / 一人一岗 / 相邻轮不同人约束对整场联合求解。返回结构与 `/api/rotation` 同构，另附：`rules` 去重排序后回显；`ruleCoverage[]` 每条规则的 `coveredCues` / `affectedRounds`（区间内无生效提示时为空数组）；`absencePlan[]` 逐轮 `absent` 缺席人员与命中的 `ruleIndexes`；`ok` 时 `rounds[].absentStaff` 本轮缺席人员、`roster[].absentRounds` 每人缺席轮次（区间外出场见 `appearances`）、`summary` 另含 `ruleCount` / `affectedRounds` / `staffAbsent`；`blocked` 时 `block` 另含 `absentStaff` 阻塞轮缺席人员，且不返回部分岗位表 |
| POST | `/api/cues/shift/preview` | 批量平移预览：校验并列出闭区间内每条提示的原号→新号及冲突号，**不写库** |
| POST | `/api/cues/shift` | 批量平移执行：校验（区间非空、新号均为安全正整数、不与区间外冲突）通过后单事务改写主键与转移引用并全量重放；冲突时返回 409 与冲突号列表，整批拒绝 |
| POST | `/api/cues/preview` | 试排预览：沿用字段校验，在内存中按提示号插入/替换草稿后分别重放现行与假设序列，**不写库**，返回生效状态变化的提示（含前后冲突原因）与最终区位变化的道具；草稿不合法时返回 400 与具体错误 |
| POST | `/api/onsite/simulate` | 现场偏差推演：入参 `{breakpoint, overrides}`（`overrides` 为 `[{prop, location}]` 或 `{prop: location}`，空 location＝沿用计划）。先按现有规则重放至断点，校验现场区位存在且普通区位不重叠，再以校正后现场状态接续重放后续提示，**不写库**；返回断点处计划/现场差异（`breakpointDiff`）、后续各提示原计划与现场推演的生效状态/冲突原因/溯源（`followCues`）、双方完整重放（`plan` / `onsite`）与最终区位差异（`finalDiff`）；现场状态不合法时返回 400 及 `validation.conflicts` 冲突区位 |

所有写操作成功后会重新执行全量重放，并返回最新状态。

## 项目结构

```
├── server.js            # Express 服务与 API
├── db.js                # SQLite 连接、建表、首次启动写入示例数据
├── replay.js            # 核心：按提示号全量重放、整组校验与断点接续重放（纯函数，试排预览与现场偏差推演共用）
├── assignment.js        # 核心：逐提示岗位表（二分图最大匹配排岗 + 资格瓶颈诊断/竞争簇分解，纯函数）
├── rotation.js          # 核心：连场轮换排班（整场生效提示联合求解：可行动用人员集合枚举 + 相邻轮次不相交的动态规划与回溯；runRotation 支持逐轮可出场人员掩码，纯函数）
├── absence.js           # 核心：临时缺席试排（缺席规则校验/归一化、区间按生效提示取并集构建逐轮缺席掩码，调用 runRotation 试排，纯函数；不写库）
├── routing.js           # 核心：换景通道规划（简单路径枚举 + 同组路径不共边的联合回溯搜索；无解区分端点不连通与通道争用并做极小不可行子集争用簇诊断，纯函数）
├── public/              # 原生 JS 前端（index.html / app.js / style.css）
├── Dockerfile           # 多阶段构建（构建阶段含编译工具，运行阶段精简）
├── docker-compose.yml   # 一条命令启动
└── data/                # SQLite 数据目录（运行时生成，勿提交）
```
